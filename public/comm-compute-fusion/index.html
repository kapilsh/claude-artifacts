Comm–Compute Fusion Patterns

GPU kernels · Distributed training and inference

Communication + compute, in one kernel

This page describes seven patterns that kernel engineers use to fuse GPU-to-GPU communication with computation. Each pattern has a diagram, a description of the mechanism, the projects that use it, and its limits.

Part 0

The problem and the building blocks

A typical distributed layer uses separate kernels. One kernel computes a full tensor and writes it to HBM. A collective kernel then moves the full tensor between GPUs. The next kernel starts only after the collective is complete.

Thus, the SMs wait while the interconnect moves data. The interconnect waits while the SMs compute. Each kernel launch and each barrier also adds latency.

A fused kernel divides the work into tiles or chunks. When a tile is ready, the kernel sends it immediately. The consumer waits on a flag for that tile, not on the full collective. Transfer and compute then overlap.

Symmetric memory

Fusion needs memory that a kernel on one GPU can read or write on another GPU. Symmetric memory gives each GPU a buffer at the same offset. A kernel calculates the address of a peer buffer from the peer rank and the local offset. It does not need a pointer table for each tensor.

Four ways to move data

  • P2P load and store. An SM reads or writes peer memory over NVLink with normal load and store instructions.
  • Multicast (NVLS). One store goes to all GPUs in the group. One multimem.ld_reduce instruction reads the value from all GPUs, and the NVSwitch adds the values. Pattern 7 describes these instructions in detail.
  • Copy engine. A DMA engine moves the data. All SMs stay available for compute.
  • GPU-initiated network (IBGDA). A GPU thread writes an RDMA request directly to the NIC. The CPU does not control the transfer. Use this method between nodes.

Signal flags

A signal pad holds one flag for each peer. The writer stores the data, applies a memory fence, and then sets the flag. The reader waits until the flag is set and then reads the data. The fence makes sure that the data is visible before the flag is visible.

Pattern 1

Tensor-parallel collective + GEMM

Fuses
All-gather with GEMM, GEMM with reduce-scatter, GEMM with all-reduce
Also called
Async TP, collective matmul, comm–GEMM overlap
Used in
Tensor parallelism (TP) and sequence parallelism (SP)

In TP and SP, an all-gather often comes before a GEMM, and a reduce-scatter often comes after a GEMM. This pattern overlaps the collective with the GEMM. The GEMM processes the data in chunks, with one chunk for each GPU.

All-gather + GEMM

Each GPU holds one row shard of the activation A and one column shard of the weight B. The GEMM starts on the local shard immediately. While it runs, the kernel or a copy engine pulls the next shard from a peer. Each shard has a flag. A GEMM tile for a shard starts when the flag for that shard is set.

GEMM + reduce-scatter

Each GPU computes a partial result for the full output. Each row chunk of the output belongs to one GPU. The kernel computes the chunk for the next peer first and stores it in the buffer of that peer. It computes its own chunk last. Each GPU then adds the received partials in fp32 and rounds the result one time.

GEMM + all-reduce

Some kernels send each output tile to all peers from the GEMM epilogue. This removes the separate all-reduce kernel. It is most useful for small and medium outputs.

Where you find it

  • PyTorch async TP. fused_all_gather_matmul, fused_matmul_reduce_scatter, and the FP8 versions. The Inductor pass micro_pipeline_tp inserts them automatically.
  • NVIDIA Transformer Engine. Userbuffers comm–GEMM overlap for Megatron-LM.
  • ByteDance Flux and TileLink. Communication in the CUTLASS prologue and epilogue.
  • Triton-distributed. AG + GEMM and GEMM + RS in Triton with OpenSHMEM-style calls.
  • ParallelKittens (ThunderKittens). AG + GEMM.
  • AMD Iris. GEMM with all-scatter and all-reduce in Triton on a symmetric heap.
  • cuBLASMp and JAX / XLA collective matmul.

Limits

Each chunk GEMM is smaller than the full GEMM. If M is small, the chunk GEMMs do not fill all SMs. If the kernel uses SMs for transfer, fewer SMs compute. A copy engine prevents this problem, but it adds a synchronization step for each chunk. The gain is largest when GEMM time and transfer time are approximately equal.

Pattern 2

All-reduce + epilogue

Fuses
All-reduce, residual add, RMSNorm, and FP8 or NVFP4 quantization
Also called
AR + RMSNorm fusion, allreduce fusion
Used in
TP inference, mostly the decode phase

During decode, each TP layer ends with an all-reduce on a small tensor. A residual add, an RMSNorm, and often a quantization step follow it. Each step is a separate kernel with an HBM round trip. At small sizes, launch latency and synchronization cost more time than the data transfer.

How the fused kernel works

The fused kernel does all four steps in one pass. Each GPU stores its partial result in its symmetric buffer. One thread block reads the same row from all peers over NVLink. It adds the values in fp32 registers. Then it adds the residual, calculates the RMS of the row, and applies the weight γ.

Last, the block quantizes the row to FP8 or NVFP4 and writes the scale factors. It also writes the new residual for the next layer. The intermediate results stay in registers and do not go back to HBM between steps.

Flags without a flag write

Some kernels use Lamport-style buffers. The kernel fills the receive buffer with negative zero before use. The reader waits until a value is not negative zero. This removes one fence and one flag write for each transfer.

One-shot, two-shot, and multicast

In a one-shot all-reduce, each GPU reads all N partials. This is fast for small messages, but each GPU reads N times the data. For larger messages, kernels use two-shot: a reduce-scatter, then an all-gather. With NVLS, multimem.ld_reduce lets the NVSwitch add the values.

Variants

  • All-reduce + MoE finalize. The kernel also adds the weighted top-k expert outputs and the shared-expert output in the same pass.
  • Quantized all-reduce. The kernel quantizes partials before the transfer and dequantizes them during the sum. AMD QuickReduce uses this method.
  • TokenWeave. Divides the batch into two parts. The all-reduce for one part overlaps the compute for the other part. It uses a fused AR + RMSNorm kernel.

Where you find it

  • TensorRT-LLM kernels in FlashInfer. trtllm_allreduce_fusion, and an MNNVL version for GB200 NVL72 racks.
  • vLLM. The fuse_allreduce_rms compile pass, on by default at O2 on Hopper and Blackwell with TP > 1.
  • SGLang. The same FlashInfer kernels.
  • PyTorch. symm_mem one-shot, two-shot, and multimem all-reduce. Inductor can write the producer output directly into the symmetric buffer.

Limits

The fused kernel helps only below a size limit. vLLM uses a default limit of 64 MB for TP = 2. One thread block must hold a full row for the RMSNorm. You must register the buffers before CUDA graph capture. The flags must reset correctly between graph replays.

Pattern 3

MoE expert parallel

Fuses
Dispatch, FP8 cast, grouped GEMM, and weighted combine
Also called
EP all-to-all, dispatch / combine kernels, single-kernel MoE
Used in
Mixture-of-experts training and inference

In expert parallelism (EP), each GPU holds a set of experts. Each token goes to its top-k experts, which are often on other GPUs. Dispatch sends the tokens to the experts. Combine returns the expert outputs and adds them with the router weights.

Fused dispatch and combine

A dispatch kernel reads each token, casts it to FP8 with block scales, and stores it directly in a slot on the destination GPU. A prefix sum of token counts gives the slot index. The kernel then increments a counter for each expert on the destination GPU. A combine kernel reads the k expert outputs for each token, multiplies each output by its router weight, and adds them.

Single-kernel MoE

The next step puts dispatch, grouped GEMM, and combine in one persistent kernel. A GEMM tile for an expert starts when the token count for that expert is final. Each output tile goes back to its source GPU when it is complete. Transfer then overlaps with the GEMM in both directions.

Between nodes

Across nodes, the GPU uses IBGDA to start RDMA transfers without the CPU. The DeepEP low-latency mode returns a receive hook. The transfer then continues without SMs while other work runs.

Where you find it

  • Dispatch and combine kernels. DeepEP (normal and low-latency modes), pplx-kernels, NCCL EP, Mooncake EP, UCCL-EP, and TensorRT-LLM wide EP.
  • Single-kernel MoE. DeepGEMM MegaMoE, ByteDance Comet, Flux MoE, and Triton-distributed MoE.

Limits

The token count for each expert is known only after routing. Kernels either exchange the counts first or size the buffers for the worst case. Load imbalance between experts makes some GPUs wait. A persistent kernel must divide its SMs between transfer, GEMM, and combine. The best division changes with the batch size.

Pattern 4

Attention and context parallel

Fuses
KV transfer, attention, and the softmax merge
Also called
Ring attention, distributed flash-decoding
Used in
Long-context training, prefill, and decode

In context parallelism (CP), each GPU holds one part of the sequence. Attention for the local queries needs the keys and values (KV) from all parts. Ring attention moves the KV blocks around a ring of GPUs.

Ring attention in one kernel

Some warps compute attention on the current KV block. At the same time, other warps or TMA copy the next KV block from the previous GPU. After each block, the kernel updates the running maximum, the running sum, and the output with online softmax. The final result is the same as attention over the full sequence.

Distributed flash-decoding

For decode with a long KV cache, each GPU holds part of the cache. Each GPU calculates a partial output Oi and its log-sum-exp value lsei. The kernel exchanges these values and merges them in the same kernel. The merge needs only a small transfer for each query.

Where you find it

  • ParallelKittens. Ring attention with in-kernel transfer.
  • Triton-distributed. Distributed flash-decoding and attention overlap kernels.

Limits

Attention on one KV block must take longer than the transfer of the next block. With a causal mask, some GPUs get less work than others. A zigzag or striped division of the sequence balances the work.

Pattern 5

Megakernels

Fuses
All operations of a layer or of a full model, including transfers
Also called
Persistent kernels, mega-kernelization
Used in
Low-latency decode

A megakernel runs a full layer or a full model as one persistent kernel on each GPU. Each SM takes tasks from a queue. A task can be a GEMM tile, an attention block, a norm, or a transfer.

How it works

Each task has a dependency counter in global memory. A task starts when its counter reaches the expected value. A transfer task stores data in a peer buffer and then increments a counter on that peer. Thus, the kernel has no launch gaps and no global barriers between operations. Some SMs start the next operation while other SMs complete the current operation.

Where you find it

  • Mirage Persistent Kernel (MPK). A compiler and runtime that converts a model into a megakernel, including multi-GPU transfers.
  • Hazy Research megakernels. Hand-written megakernels on ThunderKittens.
  • DeepGEMM MegaMoE. The same idea, applied to one MoE layer.

Limits

Megakernels are difficult to write and debug. One bad dependency stops the full kernel. The scheduler and the counters use registers, shared memory, and cycles. The largest gain is at small batch sizes, where launch latency is a large part of each step.

Pattern 6

Sharded training

Fuses
FP8 cast with all-gather; reduce-scatter with fp32 sum
Also called
FP8 all-gather, low-precision FSDP
Used in
FSDP and ZeRO training

In fully sharded data parallelism (FSDP), each GPU holds a shard of each weight. The forward pass all-gathers the full weight. The backward pass reduce-scatters the gradients.

FP8 all-gather

Each GPU casts its shard to FP8 one time, before the all-gather. The transfer then moves half the bytes of BF16. Without this change, each GPU gathers BF16 and then casts the full weight. All GPUs must use the same scale, so a small all-reduce of the maximum value comes first.

Reduce-scatter with fp32 sum

A ring reduce-scatter rounds the partial sum to BF16 at each hop. A symmetric-memory reduce-scatter reads all partials directly and adds them in fp32 registers. It rounds the result only one time.

Sequence parallelism in training uses the Pattern 1 kernels at the norm and GEMM boundaries.

Where you find it

  • torchao Float8 with FSDP2. FP8 all-gather of weights.
  • PyTorch symmetric memory. Reduce-scatter kernels that add partials in fp32 and round one time.
  • Megatron-LM with Transformer Engine. TP and SP overlap (Pattern 1) inside sharded training.

Limits

FP8 all-gather needs a scale that all GPUs agree on. This adds a small all-reduce or a delayed scale. A direct-read reduce-scatter works best inside one NVLink domain.

Pattern 7

Multicast and multimem

Fuses
Reduction and broadcast in the NVSwitch, with compute between the two steps
Instructions
multimem.ld_reduce, multimem.st, multimem.red, and copies to a multicast address
Needs
An NVSwitch with NVLink SHARP (NVLS)

A multicast object maps one address range to the memory of all GPUs in a group. The NVSwitch handles each access to this address range. It copies a store to all GPUs, or it reads from all GPUs and reduces the values. The SMs only issue the instructions. The switch does the copies and the arithmetic.

Thus, a kernel can do a full collective step with one instruction. The kernel can also apply compute between a reduce step and a broadcast step. Patterns 1 and 2 use these instructions in some of their kernels.

Instruction or methodWhat it doesTypical use
multimem.stStores one value to the same offset on all GPUsAll-gather, broadcast, second half of all-reduce, flag broadcast
multimem.ld_reduceReads the value from all GPUs; the switch reduces them (add, min, max) and returns the resultOne-shot all-reduce, reduce-scatter, first half of all-reduce, fused AR + norm
multimem.redReduces a value into the copies on all GPUs; returns nothingBarriers, counters, push-reduce of partials
Copy to a multicast addressA copy engine writes to the multicast range; the switch copies to all GPUsAll-gather and broadcast with no SMs
multimem.cp.async.bulk, multimem.cp.reduce.async.bulk, multimem.st.async, multimem.red.asyncBulk and async forms in recent PTX ISA versionsPush a full tile from shared memory, for example at the end of a GEMM
cp.async.bulk … .multicast::clusterCopies a tile into the shared memory of several CTAs in a cluster on one GPUNot NVLS. It does not use the NVSwitch.

Reduce, then broadcast

An NVLS all-reduce uses both halves. Each GPU owns 1/N of the buffer. It reads its slice with multimem.ld_reduce and gets the sum from all GPUs. Then it writes the sum to all GPUs with multimem.st. A barrier before and after the two steps makes sure that all inputs and outputs are ready.

Between the two instructions, the sum is in registers. The kernel can apply elementwise work there, for example a residual add, a bias, or a quantization step. RMSNorm needs a full row, so the kernel must divide the buffer by rows, not by bytes.

One-shot and rooted reduce

For small messages, a one-shot form is faster. Each GPU reads the full buffer with multimem.ld_reduce and keeps the result. No broadcast step occurs. A rooted reduce is the same, but only the root GPU reads. A fused AR + RMSNorm kernel can read full rows this way and complete the epilogue in registers.

Broadcast and all-gather

multimem.st writes one value to the same offset on all GPUs. In an all-gather, each GPU stores its shard at its own offset in the multicast buffer. After a barrier, each GPU has the full tensor. Each GPU sends its shard one time, and the switch makes the copies.

A copy engine can also write to the multicast address. This all-gather uses no SMs, so a GEMM can use all SMs at the same time. A root GPU can use the same method to broadcast weights or other data to the group.

Push-reduce and barriers

multimem.red adds a value into the copies on all GPUs and returns nothing. A barrier uses this method. Each GPU adds 1 to a multicast counter with release semantics. Then each GPU waits until its local copy of the counter is N or more. This barrier needs one instruction from each GPU, not N − 1 separate flag writes.

A GEMM epilogue can use the same method to add its partial tiles into the output on all GPUs. The output must be zero before the GEMM, and a barrier must come after it. The order of floating-point additions can change between runs.

Bulk and async forms

Recent PTX ISA versions add bulk and async forms of these instructions. A bulk form moves a full tile from shared memory to the multicast address. This matches the TMA store at the end of a GEMM, so an epilogue can broadcast or reduce a complete output tile with one instruction.

Do not confuse these instructions with the .multicast::cluster option of cp.async.bulk. That option copies a tile into the shared memory of several CTAs in a cluster on one GPU. It does not use the NVSwitch.

Where you find it

  • NCCL. The NVLS algorithms for all-reduce, reduce-scatter, and all-gather. The NCCL Device API Multimem mode gives the same access to user kernels.
  • PyTorch symmetric memory. multimem_all_reduce_ (reduce, then broadcast), multimem_one_shot_all_reduce, multimem_one_shot_reduce_out (rooted), multimem_all_gather_out, the copy-engine multicast all-gather, and a multimem.red barrier.
  • TokenWeave. A fused AR + RMSNorm kernel that uses multimem instructions.
  • ParallelKittens. All-reduce with in-network compute on NVSwitch.

Limits

Multicast needs an NVSwitch with NVLS, for example in HGX H100, H200, and B200 systems or in GB200 NVL72 racks. It does not work over PCIe or over direct NVLink without a switch. The driver creates multicast objects with a minimum size granularity, and the number of objects is limited. Thus, libraries allocate one large multicast pool and divide it.

The vector forms need aligned addresses, for example 16 bytes. The switch supports only some operations and data types. For BF16 and FP16, check the accumulation precision of the instruction form that you use.

Terms

SM
Streaming multiprocessor. The GPU unit that runs thread blocks.
NVLS
NVLink SHARP. The NVSwitch does multicast and reduction for a GPU group.
MNNVL
Multi-node NVLink. One NVLink domain across a rack, for example GB200 NVL72.
IBGDA
InfiniBand GPUDirect Async. A GPU thread sends RDMA requests to the NIC directly.
TMA
Tensor Memory Accelerator. A hardware unit that copies tiles asynchronously.
Symmetric memory
Buffers at the same offset on each GPU, so a kernel can calculate peer addresses.
One-shot / two-shot
All-reduce in one read phase, or in a reduce-scatter phase plus an all-gather phase.
