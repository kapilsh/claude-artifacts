Module 1 · OS fundamentals for AI systems

How the machine is built

Everything the kernel does later (page tables, scheduling, I/O) is a way of managing this hardware. This module covers what's physically in the box, how far apart things are in nanoseconds, and which wires your bytes cross on the way to the GPU.

0The map: your two machines

Your two boxes are the two basic designs. The x86 + RTX 4090 is the classic discrete design: the CPU and GPU each have their own memory, joined by a PCIe link that's slower than either memory. The DGX Spark is a unified design: one pool of LPDDR5x behind a coherent fabric. The GPU reaches it over NVLink-C2C, and there's no PCIe hop between CPU and GPU. Datacenter nodes (8 GPUs + NICs behind PCIe switches, NVLink between GPUs) mix both ideas, and GB200 is a big Spark: Grace and Blackwell joined by C2C.

Where this shows up in your stack On the 4090, tensor.cuda() crosses the slowest wire in the box. On Spark the same call copies DRAM to DRAM inside one memory pool. It can still be expensive, because every byte is read and written through the same 273 GB/s. Most of this course is about which of those two worlds a given API call lives in.

1Cores, cache lines, and coherence

What it is. A core runs one instruction stream (two with SMT/hyperthreading). It owns registers and small, fast private caches (L1, L2), and shares a larger L3 with its neighbours. Memory moves between DRAM and caches only in fixed blocks called cache lines: 64 bytes on both your x86 box and the Spark's Arm cores. Read one byte and the hardware fetches its whole 64-byte line.

How it works. Each line in a cache has a state. The common protocol is MESI: Modified, Exclusive, Shared, Invalid. Before a core writes a line, every other core's copy must be invalidated. If two cores keep writing different variables that happen to share a line, the line bounces between their caches on every write. That's false sharing, and it can make a "parallel" loop slower than a serial one.

Hybrid cores. Both of your CPUs mix big and small cores. The 13900K has 8 P-cores (CPUs 0–15 with hyperthreads) and 16 E-cores (CPUs 16–31). The Spark has 10 Cortex-X925 and 10 Cortex-A725 in two clusters, interleaved in the CPU numbering: CPUs 0–4 and 10–14 are A725 (2.8 GHz), and 5–9 and 15–19 are X925 (3.9 GHz). So CPU 0 is a little core, which matters if a script pins to it. NVIDIA's Spark optimization guide specifically warns against concurrent writes to the same cache lines from different cores, "especially ones in different clusters."

Why it matters for AI workloads: your hot host-side code is single-threaded more often than you'd think: the Python launch loop, the NCCL proxy thread, a DataLoader collate. Which core it lands on (P vs E, near vs far cluster) and whether its data stays in cache can change step time measurably. The drill shows a 2× difference in one copy path just from picking an E-core.
Where this shows up in your stack Strided CPU tensor ops (t[:, ::2], a non-contiguous .permute()) waste most of every 64-byte line they fetch, which is why .contiguous() before CPU-side work pays off. Lock-free host-memory flags polled by both CPU and GPU (NCCL proxy FIFOs, cudaHostAlloc'd semaphores) are laid out one per cache line for exactly this reason.

2Latency and bandwidth, in orders of magnitude

What it is. Every layer, from register to network, trades distance for capacity. Two numbers describe each one: latency (how long until the first byte arrives) and bandwidth (bytes per second once data is flowing). You don't need exact values. You need the ratios, because they decide whether the fix is "batch it," "overlap it," or "keep it out of that layer."

How to read it. Each step down the hierarchy costs roughly 10× more latency. Hiding latency always works the same way: keep many requests in flight (out-of-order CPUs, GPU warps, NVMe queues, NCCL channels) so bandwidth, not latency, sets the speed.

Why it matters for AI workloads: a 4090 does ≈80 TFLOP/s of dense bf16 work, roughly 80,000 flops per nanosecond. During one 100 ns DRAM miss on the host, the GPU could have done eight million flops. Host-side latency is invisible only while the GPU has a deep queue of work. As soon as the queue drains, every microsecond of host latency becomes GPU idle time (Module 3 builds on this).
Where this shows up in your stack A cudaLaunchKernel costs a few µs of CPU time. That's why a step made of thousands of small kernels is launch-bound, and why CUDA graphs and torch.compile's kernel fusion help. Small NCCL all-reduces are latency-bound (µs per hop), and large ones are bandwidth-bound (GB/s per link). NCCL's algorithm choice (ring vs tree) and NCCL_ALGO tuning sit on that boundary.

3NUMA: not all memory is equally close

What it is. In a multi-socket server, each CPU socket has its own memory controllers and its own PCIe root complexes. Memory and devices attached to your socket are local, and those on the other socket are remote: you reach them across the socket interconnect (Intel UPI, AMD Infinity Fabric). That's Non-Uniform Memory Access. Linux exposes each socket (or sub-socket domain) as a NUMA node with its own CPUs, memory, and a numa_node attribute on every PCIe device.

How it works. By default Linux allocates a page on the node of the CPU that first touches it ("first-touch" policy). The scheduler tries to keep threads near their memory but doesn't guarantee it. A remote access adds roughly 50–100% latency, and the socket link has less bandwidth than local memory, shared by everyone crossing it.

The GPU and NIC have NUMA nodes too. Each GPU and each NIC hangs off one socket's root complex. Inter-node NCCL traffic flows GPU memory → PCIe → NIC → wire. If the GPU and its NIC share a PCIe switch, that path never touches a CPU. If they sit on different sockets, every byte crosses the socket link or bounces through host memory, and it competes with everything else using that link.

Why it matters for AI workloads (completion criterion #3): NCCL reads the PCIe/NVLink topology at init and pairs each GPU with its closest NIC. It enables GPUDirect RDMA (NIC reads/writes GPU memory directly) only when the GPU-to-NIC distance is within NCCL_NET_GDR_LEVEL. When the distance is too far, it stages through host memory instead. The proxy thread that drives the NIC, and the pinned bounce buffers it uses, should also live on the GPU's NUMA node. Get placement wrong and you lose bandwidth twice: the transfer crosses the socket link, and the CPU-side helper runs on remote memory.
Where this shows up in your stack nvidia-smi topo -m prints each GPU's CPU and NUMA affinity and its distance to every NIC. NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=INIT,GRAPH logs which NIC each rank picked and whether GDR is on (look for GDRDMA in the channel lines). Launchers that bind each rank to its GPU's NUMA node (numactl --cpunodebind=N --membind=N, or Slurm's --cpu-bind) keep DataLoader workers and pinned buffers local. NCCL also honors the CPU affinity it inherits (NCCL_IGNORE_CPU_AFFINITY=0 by default), so a bad launcher binding becomes NCCL's binding.

Your machines: the i9-13900K and the Spark each expose one NUMA node, so true cross-NUMA effects only show up on multi-socket servers. The drill confirms this, then runs a near/far core comparison instead (P-core vs E-core on x86, X925 vs A725 on Spark). On x86 the CPU doing the copy matters: an E-core halves pageable throughput. On the Spark it doesn't (≈59 GB/s on either core type), because the pageable path there isn't a CPU memcpy. The core still matters on the Spark for launch-bound work, by 5×, as Module 3 measures.

4PCIe: lanes, generations, topology

What it is. PCIe is a packet-switched, point-to-point serial bus. A link is 1–16 lanes wide. Each generation doubles the per-lane rate. The CPU's root complex is the root of a tree. Switches fan one upstream link out to several devices, and devices under the same switch can talk peer-to-peer without going up to the CPU.

GenGT/s per lanex16, per directionTypical device
3.08≈16 GB/sV100-era GPUs, 100G NICs
4.016≈32 GB/sRTX 4090, A100, Gen4 NVMe (x4 ≈ 8 GB/s)
5.032≈63 GB/sH100/B200 host link, 400G NICs; Spark's CX-7 (as 2× x4)
6.064≈121 GB/semerging (800G NICs)

Real throughput is about 75–85% of these numbers after packet headers and flow control. Your 4090 measures ≈20 GB/s pinned H2D against a 32 GB/s peak (see the drill).

Links downtrain when idle. The drill on your 4090 reported pcie.link.gen.current = 1 at idle. That's power management (ASPM / dynamic link speed), not a fault. Check the link under load before blaming a riser or slot. A link that stays at x8 or Gen3 under load is a real problem, and it's a common one.

Why it matters for AI workloads: PCIe is usually the narrowest pipe a tensor crosses. The H2D link sets a ceiling on how fast you can feed a discrete GPU from host memory, and on how fast you can offload optimizer state or KV cache to the CPU. In multi-node training, the GPU↔NIC PCIe path is part of every inter-node all-reduce.
Where this shows up in your stack ZeRO-Offload / FSDP CPU offload, KV-cache offload to host, and pin_memory'd DataLoader batches are all PCIe-bound on discrete GPUs. A rough rule: if per-step host↔device traffic divided by ≈20 GB/s (Gen4) or ≈50 GB/s (Gen5) is close to your compute time, the step is PCIe-bound, and overlap is the only fix. The NCCL_P2P_LEVEL and NCCL_NET_GDR_LEVEL settings take these same codes (PIX, PXB, PHB, SYS) as thresholds.

5NVLink and NVLink-C2C

What it is. NVLink is NVIDIA's GPU-to-GPU link: point-to-point, much wider than PCIe, and switched through NVSwitch within a node or rack. On Blackwell each GPU gets 1.8 TB/s of NVLink bandwidth in total (both directions). NVLink-C2C (chip-to-chip) applies the same technology between a CPU die and a GPU die, with cache coherence: the CPU and GPU can each cache lines from the other's memory, and hardware keeps those copies consistent.

SystemCPU↔GPU linkBandwidthCoherent?
x86 + RTX 4090PCIe 4.0 x16≈32 GB/s/dirNo: separate memories; copies required
x86 + H100/B200PCIe 5.0 x16≈63 GB/s/dirNo
GH200 / GB200 (Grace)NVLink-C2C900 GB/s totalYes. The GPU still has its own HBM
DGX Spark (GB10)NVLink-C2C≈600 GB/s aggregateYes. The GPU has no own memory: everything is LPDDR5x at 273 GB/s

How Spark differs. GB10 is two dies in one package. The S-die (MediaTek-built: CPU, memory controller, PCIe) and the G-die (Blackwell GPU, 24 MB L2) are joined by C2C. The GPU's L2 is physically tagged and caches system physical addresses. The GPU translates virtual addresses through ATS (Address Translation Services) with the system MMU, the same page tables the CPU uses (Module 2). C2C is faster than memory here, so on Spark the LPDDR5x is the bottleneck, not the link. (nvidia-smi c2c -s on the Spark lists 8 C2C links at 43.125 GB/s each, 345 GB/s in total, without saying whether that's per direction. Either way it's above 273 GB/s.)

Why it matters for AI workloads: on a discrete GPU, "memory-bound" means HBM/GDDR bandwidth (≈1 TB/s on the 4090), and host↔device transfers are a separate, much slower problem. On Spark there's a single budget: 273 GB/s shared by CPU and GPU. Decode for a large LLM is memory-bound, so token rate is roughly bandwidth divided by bytes read per token, and a CPU thread streaming through memory at the same time takes from the same budget.
Where this shows up in your stack On Spark, cudaMalloc and malloc come from the same DRAM, and cudaMemGetInfo under-reports what you can allocate because it doesn't count page cache the OS could reclaim (NVIDIA lists this as a known issue). In NCCL across two Sparks, NVIDIA states GPUDirect RDMA is not supported: cudaMalloc memory isn't coherently accessible to PCIe devices, so nvidia-peermem, dma-buf and GDRCopy don't work. NVIDIA's recommended fallback is to allocate communication buffers with cudaHostAlloc and register those with the NIC.

6DMA, copy engines, and why pinned memory matters

What it is. DMA (direct memory access) means a device reads or writes host memory itself, without a CPU loop doing the copying. NVMe controllers, NICs and the GPU's copy engines are all DMA engines. The CPU writes a descriptor ("copy N bytes from physical address A to B") into a queue, and the device does the rest.

How it works. A device can't use your process's virtual addresses on its own. It needs bus/physical addresses that will stay valid for the whole transfer. Ordinary malloc memory is pageable: the kernel can move a page, swap it out, or not have allocated it yet (Module 2 explains why). Pinned (page-locked) memory from cudaHostAlloc or cudaHostRegister is locked in place and pre-mapped for the device, so the driver can hand its addresses straight to the copy engine.

For pageable memory, the CUDA driver keeps its own small pinned staging buffers. A pageable H2D copy is really two copies: the CPU memcpy's chunks into staging, and the copy engine DMAs each chunk across PCIe, pipelined.

Why it matters for AI workloads (completion criterion #1): a pageable copy is slower because (a) the bytes cross DRAM twice (user buffer → staging → PCIe), (b) throughput is capped by one CPU core's memcpy speed, and (c) the copy engine waits on the CPU between chunks. It can't be truly async because the driver can only DMA from pinned memory. Someone has to stage the pageable bytes, and that someone is your calling thread, so cudaMemcpyAsync doesn't return until the data has been staged. The CUDA docs say pageable async copies "might be synchronous with respect to host." Your 4090 shows it: the pageable call held the thread for ≈120% of the pinned transfer time, while the pinned call returned in ≈3 µs.
Where this shows up in your stack tensor.to("cuda", non_blocking=True) overlaps with compute only if the source is pinned. That's what DataLoader(pin_memory=True) buys you: a background thread copies each batch into pinned memory so the main thread's H2D copy becomes a real DMA. In nsys, a pageable copy shows up as Memcpy HtoD (Pageable) with the CPU stuck in the API call. Pinning has a cost: pinned pages can't be swapped or reclaimed, so pinning tens of GB starves the page cache (Module 2), and on Spark it comes out of the same 128 GB the GPU uses.

7Interrupts vs polling

What it is. When a device finishes work (a packet arrived, an NVMe read completed, a copy finished), it has two ways to tell the CPU. It can raise an interrupt: modern devices use MSI-X, a memory write that becomes an interrupt on a chosen core, with one vector per queue. Or the CPU can poll: spin on a completion flag in memory.

How it works. An interrupt stops whatever that core was running, enters the kernel's handler, and usually wakes a sleeping thread, which the scheduler then has to run. End to end that's microseconds, and more if the target core was busy or in a deep sleep state. Polling reacts in the time it takes to see a cache line change (≈100 ns), but it burns a whole core. High-rate devices compromise: interrupt coalescing (one interrupt per batch), NAPI in the network stack (switch to polling under load), and per-CPU NVMe queues (the interrupt lands on the core that asked).

Why it matters for AI workloads: the latency-critical paths in your stack poll. NCCL kernels spin on flags in GPU or host memory, the NCCL proxy thread busy-polls the NIC's completion queue, and RDMA (Module 4) is built on user-space polling instead of interrupts. The trade-off is that those spinning threads need a core to themselves. If the scheduler shares that core with a DataLoader worker, latency jumps (Module 3).
Where this shows up in your stack cudaStreamSynchronize spin-waits by default for a short time and then may yield. cudaSetDeviceFlags(cudaDeviceScheduleBlockingSync) makes the CPU sleep until the GPU interrupts instead: less CPU burn, more wake-up latency. /proc/interrupts shows which cores take the NIC's and GPU's interrupts, and IRQ affinity is set in /proc/irq/*/smp_affinity (Module 3).

8The end-to-end data path

Here is everything above combined: a checkpoint shard or a training batch travelling from disk to a GPU and then to another GPU or node. At each hop, notice who moves the bytes (a CPU core or a DMA engine), and how many times they're copied through DRAM.

Why it matters for AI workloads: each extra copy through host DRAM costs memory bandwidth and usually a CPU core. GPUDirect Storage and GPUDirect RDMA (Module 4) exist to cut out exactly those copies. Faster checkpoint loading, input pipelines and inter-node communication all come down to removing hops in this diagram, or overlapping the ones you can't remove.
Where this shows up in your stack torch.load of a pickled checkpoint takes the full path: read into page cache, copy to Python-owned buffers, then H2D. safetensors with mmap skips the user-buffer copy (Module 2). On the network side, NCCL's NET/IB : GPU Direct RDMA enabled log line means the "bounce through host" step below has been removed.

What to look for

  1. Topology. Find the cache-line size, core types, NUMA node count, and the numa_node / local_cpus of the GPU and NIC. In nvidia-smi topo -m, read the CPU Affinity column.
  2. Bandwidth. Pinned should beat pageable, and the pinned call's "CPU blocked" time should be microseconds while the pageable one is about the whole transfer. That's criterion #1 on your own hardware.
  3. Placement. Pageable throughput follows the CPU core, and pinned throughput doesn't. On a multi-socket server with numactl, cross-node memory also cuts pinned bandwidth, because the DMA has to cross the socket link.

?Self-check

Answer out loud first, then open the answer.

You wrote x.to("cuda", non_blocking=True), but nsys shows the copy and the next kernel running back to back with no overlap, and the CPU stuck in cudaMemcpyAsync. What's happening, and what's the fix? criterion #1
x is in pageable memory. The copy engine can only DMA from pinned memory with stable physical addresses, so the driver has your calling thread memcpy the data, chunk by chunk, into its own pinned staging buffers. The call returns only after the last chunk is staged, so it's effectively synchronous, and bandwidth is capped by one core's memcpy plus a second pass through DRAM. Fix: put the source in pinned memory (pin_memory=True in the DataLoader, x.pin_memory() once for reused buffers, or allocate with torch.empty(..., pin_memory=True)). Then the call only enqueues a DMA descriptor and returns in microseconds.
Why can't the GPU's copy engine just DMA straight from a malloc'd buffer?
A DMA engine works on bus/physical addresses that must stay valid for the whole transfer. Pageable memory doesn't guarantee that: its pages might not be allocated yet, the kernel can migrate or swap them at any time, and the IOMMU mapping for the device might not exist. Pinning locks the pages in place and maps them for the device ahead of time. (Module 2 covers the page-table side of this.)
On an 8-GPU, 2-socket node, NCCL all-reduce across nodes is 40% slower than on an identical node. topo -m shows GPU4↔mlx5_2 as SYS on the slow node and PIX on the good one. Explain. criterion #3
On the slow node, GPU4's traffic to its NIC crosses the socket interconnect, so it isn't the NIC on the same PCIe switch. Either the NIC is cabled/slotted differently, or the rank-to-NIC mapping was forced (e.g. by NCCL_IB_HCA) to a far NIC. At SYS distance NCCL normally disables GPUDirect RDMA and stages through host memory instead. Every byte then crosses UPI, which is shared and slower than local PCIe, and bounces through DRAM. If the proxy thread and bounce buffers also sit on the far socket, you pay for remote memory too. Fixes: correct the hardware or NIC mapping, let NCCL auto-select, and bind each rank's CPU and memory to its GPU's NUMA node.
Two threads each increment their own counter, ctr[0] and ctr[1], in a shared int64 array. Adding the second thread makes it slower. Why?
False sharing. Both counters sit in the same 64-byte cache line, so every write by one core invalidates the other core's copy, and the line bounces between their caches (tens of ns per bounce, more across clusters or sockets). Pad each counter to its own 64-byte line, or keep per-thread counters in registers or locals and combine them at the end.
A 70B-parameter bf16 checkpoint is 140 GB. Roughly how long, at best, to get it from one Gen4 NVMe into GPUs, versus from a warm page cache over PCIe Gen5 x16? What does that suggest?
NVMe at ~7 GB/s: ~20 s just to read the disk, and that's the bottleneck. From page cache at ~50 GB/s achieved per Gen5 x16 link: ~3 s if one GPU had to take all of it, less when 8 GPUs load their own shards in parallel over separate links. So cold loads are disk-bound (use multiple drives, or keep checkpoints in page cache or tmpfs on the node), warm loads are PCIe-bound, and extra CPU copies (pickle → Python buffers) push both toward CPU-bound. Module 4 covers dropping caches to measure each case.
On DGX Spark, what does "H2D bandwidth" actually measure, and what else is competing for the same resource?
Both source and destination are in the same LPDDR5x pool, so an "H2D" copy reads and writes the same DRAM, and the 273 GB/s is shared between the read and the write. In practice the copy engine is the limit: the drill measures ≈60 GB/s for cudaMemcpy on the Spark, while SMs reading the same memory in place reach 231–262 GB/s. CPU threads (data prep, tokenization, the Python process) and the GPU's own kernels draw from that same 273 GB/s. On Spark the question isn't PCIe speed. It's whether a copy is needed at all, since the GPU can access system memory coherently over C2C (Module 2: ATS, HMM).
Why does NCCL's proxy thread busy-poll the NIC's completion queue instead of waiting for an interrupt, and what does that imply for how you place threads?
An interrupt plus a thread wake-up costs microseconds, and more if the core was asleep or busy. Spinning on a completion entry in memory reacts in about the time it takes a cache line to change. For latency-bound collectives, those microseconds are a big fraction of the operation. The price is a dedicated core: if the scheduler puts a DataLoader worker or another rank on that core, the proxy gets descheduled and latency spikes. Keep proxy and launch threads on reserved, NUMA-local cores (Module 3).
