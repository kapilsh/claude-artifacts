PyTorch CUDA Graphs

This document tells how PyTorch captures CUDA work into a graph and replays it. It covers the C++ core, the allocator, the RNG, the Python APIs, and Inductor CUDA graph trees.

Source: pytorch@9c0fed7 (2026-10-29) Style: ASD-STE100 (Simplified Technical English)

01 · Overview

The layers

A CUDA graph is a record of GPU work. CUDA records the work when a stream is in capture mode. The record keeps kernel arguments, which include device addresses. Replay sends all the recorded work with one CPU call.

Raw capture is not sufficient for PyTorch. Two components keep CPU state that capture does not record: the caching allocator and the RNG generator. PyTorch adds a wrapper that makes these two components safe for replay.

Problem in raw capturePyTorch solutionSection
Captured kernels keep device addresses. The allocator can give those addresses to other tensors after capture.Route capture allocations to a private pool. Keep the pool until no graph uses it.05
The allocator queries CUDA events to recycle cross-stream blocks. Event queries are illegal during capture.Defer those frees until capture ends.06
RNG kernels receive seed and offset as values. Replay would repeat the same random numbers.Give kernels pointers to device tensors. Refill the tensors before each replay.07
The graph has fixed input and output addresses.Copy new inputs into static tensors. Return static outputs.10, 12

03 · Procedure

Capture begin: the sequence

with torch.cuda.graph(g): starts this sequence. The order of steps 8 and 9 is important.

  1. Synchronize the device. Release cached blocks. This gives the graph pool the largest possible free memory. graphs.py · graph.__enter__
  2. Set a side stream as the current stream. The default stream cannot capture. capture_begin: TORCH_CHECK(stream != default)
  3. Allocate num_rng_states (default 8) seed/offset tensor pairs. Do this before pool routing starts, so these tensors come from the global pool. CUDAGeneratorCaptureState::initialize
  4. Select the pool ID. A user pool has the form {0, uid}. A graph-created pool has the form {uuid, 0}. MemPool::graph_pool_handle
  5. Start pool routing on the device allocator and the host allocator. beginAllocateToPool
  6. Start stream capture. Tell the allocator that a real capture is active. cudaStreamBeginCapture · markCaptureBegin
  7. Read the capture ID from CUDA. Add the graph to the global registry under that ID. _currently_capturing_graphs
Caution
Pool routing must start before cudaStreamBeginCapture. If the order is reversed, an autograd thread can free a block in the gap. The allocator then records a CUDA event on a capturing stream. That call is illegal and the capture fails.
Note
With backend:cudaMallocAsync, PyTorch ignores a user pool ({0, uid}). CUDA manages graph memory through the default async pool. Instantiation uses cudaGraphInstantiateFlagAutoFreeOnLaunch for this backend.
04 · Threads

The capture registry and capture modes

A capture can include work from more than one thread. Autograd runs backward ops on worker threads. A thread-local "current graph" is therefore not correct.

PyTorch uses a global map, _currently_capturing_graphs, from CUDA capture ID to CUDAGraph*. A mutex protects it. Any thread can find the active graph: it reads the capture ID of its current stream and looks up the map.

05 · Memory

Private memory pools

Captured kernels keep their device addresses. Replay writes to the same addresses. Thus no other tensor can use those addresses while the graph exists. The allocator makes sure of this with a PrivatePool per graph (or per shared pool ID).

Rules of the private pool

  • During capture, the pool frees and reuses blocks as usual. Replay uses the addresses in the same order, so this reuse is safe.
  • The filter matches the capture ID of the stream. A side stream that joins the capture (through an event wait) has the same capture ID. Its allocations also go to the pool.
  • A stream that does not capture goes to the global pools, also during a capture.
  • allocation_scopes_ is not a "capture active" signal. torch.cuda.use_mem_pool, NCCL registration, and Inductor warmup also add scopes. The allocator uses a separate capture_tracker_ (markCaptureBegin/End) for real captures.

Pool sharing

Two or more graphs can share one pool. Pass pool=g1.pool() or pool=torch.cuda.graph_pool_handle() to capture_begin. Memory use goes down. But the graphs must replay in capture order: graph B can use memory that graph A considers free after A ends.

Caution
With a shared pool, do not keep an output of graph A and then replay graph B, if B was captured after A's output was free. B can write over the output. CUDA graph trees remove this restriction (section 12).

retain_pool(pool) lets one graph hold a reference to a second pool during capture. reset() releases every pool in retained_mempool_ids_.

06 · Memory

Frees during capture

A block that was used on more than one stream (record_stream) has stream_uses. Outside capture, the allocator records one event per stream. process_events() queries the events and frees the block when all events are complete.

cudaEventQuery is illegal during capture. Thus the allocator changes its behavior when is_capture_context() is true:

PathOutside captureDuring capture
prepare_for_mallocCalls process_events().Does not call it. With graph_capture_record_stream_reuse, calls free_safe_blocks_in_capture().
free_locked, block with stream_usesinsert_events(block).Adds the block to deferred_blocks. The block is not free until capture ends.
free_locked, single-stream blockfree_block.free_block (same).
After capture—The next process_events() (first malloc outside capture) calls insert_events_deferred_until_no_capture: remove stream uses made during capture, record events for older uses. With graph_capture_record_stream_reuse, endAllocateToPool does this at capture end.

Stream uses made during capture are complete at capture end. cudaStreamEndCapture fails if a side stream does not join back. Thus the allocator removes those uses without events.

Note
The option graph_capture_record_stream_reuse:True inserts empty "free marker" nodes into the graph. The allocator walks the graph backward from the current stream to find blocks that are safe to reuse during capture. This option does not work with conditional nodes (issue #175001).
07 · RNG

Graph-safe RNG

PyTorch CUDA RNG uses Philox. A kernel needs a seed and an offset. In eager mode, the host passes both as values. Then it increments the offset. If capture recorded the values, each replay would make the same numbers.

During capture, philox_cuda_state() gives the kernel two pointers to device tensors and one intra-graph offset value. Before each replay, PyTorch writes the current seed and offset into those tensors.

Data structures

CUDAGeneratorStateGenerator (shared by graph-safe aliases)seed_, philox_offset_per_thread_. Eager state.

PhiloxCudaStateKernel argumentcaptured_ flag. Values (eager) or pointers + intra-graph offset (captured).

Limits

  • The graph allocates num_rng_states slots before capture (default 8). Each distinct generator state takes one slot. If the capture uses more, PyTorch raises "CUDA graph RNG state limit exceeded". capture_end_pre removes unused slots.
  • Each increment is rounded up to a multiple of 4. Philox makes 4 values per call.
  • set_current_seed during capture is allowed only with the same seed.
  • RNG inside a conditional node body is not supported. end_capture_to_conditional_node raises an error.
  • Python keeps the RNG buffers alive with retain_object(..., synchronize_before_release=True). A replay that is still running can thus read them safely.
08 · Execution

Instantiate and replay

CUDAGraph::instantiateC++
cudaGraphInstantiateWithFlags(&graph_exec_, graph_,
    cudaGraphInstantiateFlagAutoFreeOnLaunch     // cudaMallocAsync: free unfreed graph allocs on relaunch
  | cudaGraphInstantiateFlagUseNodePriority);    // keep per-kernel stream priority (not on ROCm)

With keep_graph=True, a second instantiate() destroys the old exec and makes a new one. Use this after you edit the raw cudaGraph_t. PyTorch does not track such edits.

Replay procedure

  1. Python: if check_input_liveness is on, make sure no captured input tensor is freed. _tracker.check_alive
  2. Python: if no exec exists (keep_graph=True), instantiate now. This adds latency to the first replay. CUDAGraph.replay
  3. Python: run replay-start hooks. Record the current stream if retained objects need a sync before release.
  4. C++: set the device to the capture device. OptionalDeviceGuard
  5. C++: run replay_prologue for each captured generator state. section 07
  6. C++: launch the exec on the current stream. This stream can be different from the capture stream. cudaGraphLaunch
  7. Python: run replay-end hooks (also on error).
Caution
If you replay on a stream that is not the capture stream, first make that stream wait for the capture stream. Work queued before capture can still use memory that the graph uses.
Note
Replay does not run CPU code. The allocator, autograd, and Python see no change. Output tensors keep the same storage. Each replay writes over the previous output.
09 · Teardown

Reset and teardown

~CUDAGraph() calls reset(). reset() warns on error and does not throw, because it runs in a destructor. It does these steps in this order:

  1. Clear captured_generator_states_.
  2. If capture_id_ != 0, remove the graph from the capture registry.
  3. If capturing_to_pool_, call endAllocateToPool (device and host). This applies to an abandoned capture.
  4. Clear cuBLAS workspaces cached for the capture stream. Live workspaces would keep the pool from being freed.
  5. Call releasePool for each retained pool. Release the host pool.
  6. Destroy the template (cudaGraphDestroy) and the exec (cudaGraphExecDestroy) if they exist.
Caution
cudaGraphDestroy and releasePool are illegal while another stream captures in global mode. Python garbage collection can run at any time. make_graphed_callables avoids reference cycles for this reason: refcount frees the graphs at a known point.
Caution
Native callers must wait for pending replays before reset or destruction. The C++ class does not synchronize. On ROCm, the destructor calls cudaDeviceSynchronize.
10 · Autograd

make_graphed_callables

This API captures forward and backward of one or more callables. It returns callables that replay the graphs inside one autograd.Function.

Mechanism

  • Static input surface. User args + module parameters. Forward copies a new arg only if its data_ptr differs. Parameters must not move after capture.
  • Backward capture. torch.autograd.grad runs inside torch.cuda.graph. Inputs are the static surface entries that need grad. grad_outputs are static empty_like tensors.
  • Train/eval switch. For an nn.Module, the new forward replays only if module.training equals the state at capture. Otherwise it runs the original forward.
  • No cycles. The graphs are arguments to Graphed.apply, not closure cells. The module is held by weakref. This gives deterministic graph destruction (see section 09).

No module hooks at call time.Hooks would run during capture only, not on replay.

Autocast cache must be off.Cached casts would be graph-pool tensors with a lifetime that the graph does not control.
sample_args contain only tensors.Non-tensor values are fixed in the graph.

11 · Control flow

Conditional nodes (CUDA ≥ 12.4)

A normal graph has fixed control flow. CUDA 12.4 adds conditional nodes: IF and WHILE. A device-side value selects the path at replay time. PyTorch uses them for torch.cond and torch.while_loop inside a capture.

  1. Get the capturing cudaGraph_t. Create a conditional handle. cudaGraphConditionalHandleCreate
  2. Launch a 1-thread kernel that copies the predicate tensor into the handle. CUDAGraph.cu
  3. Get the current capture dependencies. Add a conditional node after them. Make the node the new dependency of the capture stream. cudaGraphAddNode · cudaStreamUpdateCaptureDependencies
  4. Create a child stream. Move pool routing to a filter for the child capture ID. Start capture into the body graph.
  5. Run the body. For WHILE, copy outputs into the carried tensors and set the handle again from the new predicate.
  6. End child capture. Pop the stacks. Restore the parent filter. Raise an error if RNG was used in the body.

Stacks (conditional_node_streams_, conditional_graph_capture_ids_, conditional_node_handles_) support nested conditionals. CUDAGraphCaptureControlFlowOpDispatchMode intercepts higher_order.cond and higher_order.while_loop during capture.

12 · Compiler

CUDA graph trees (Inductor)

torch.compile(mode="reduce-overhead") uses CUDA graph trees. One CUDAGraphTreeManager exists per device. All its graphs share one private pool. The manager removes two restrictions of a shared pool: fixed replay order, and dead intermediate outputs.

Dispatch procedure — CUDAGraphTreeManager._run

  1. If recording or warmup is in progress, try to end it. End is possible if all outputs of the current node are dead, or a new generation started.
  2. If the function mutates inputs that the tree does not manage, run it eager. If the re-record limit is reached, run it eager.
  3. If the function is not warmed up, run warmup. If the tree is in EXECUTION, restore the allocator checkpoint first.
  4. Look for a child node of the current node for this function. Run check_invariants(new_inputs) on each. On success, replay it.
  5. If no child passes, count a re-record (except StaticInputIdxMismatch). Try to end the current execution. Restore the checkpoint.
  6. Record a new child node under graph_capture_lock.
Invariant check resultMeaning
SUCCESSReplay is safe.
CudagraphManagedIdxMismatchAn input that came from a prior graph output has a different address.
StaticInputIdxMismatchA parameter or mark_static_address tensor has a different address. Does not count to the limit.

Generations

A generation is one invocation of the compiled model. The manager reads GenerationTracker.generation from Dynamo, or the counter from torch.compiler.cudagraph_mark_step_begin(). At a new generation, the manager ends the current path. Outputs of the old path that are still live get a storage access error message:

Error textRuntimeError
Error: accessing tensor output of CUDAGraphs that has been overwritten by a subsequent run.

To keep an output past the next run, clone it. A forward with a pending backward does not start a new generation, unless the user calls mark-step.

13 · Distributed

NCCL collectives in capture

  • NCCL >= 2.9.6 is necessary. Older versions raise NotImplementedError (errorIfCapturingNonCapturableNCCL).
  • During capture, ProcessGroupNCCL does not enqueue work to the watchdog. The watchdog queries events, and the query is illegal in global capture mode (Note [cuda graph capture and workEnqueue]).
  • Coalesced collectives check capture status. Some host-side bookkeeping runs only when capture_status == None.
  • On ROCm, the watchdog skips hipEventQuery while any capture is active (is_graph_capture_active()). An older HIP runtime can otherwise invalidate the capture.
