PyTorch Allocator Map

This page shows each memory allocator in PyTorch. It shows how a tensor gets its memory, how each allocator caches memory, and how a custom MemPool connects to the CUDA caching allocator.

Device memory Pinned host memory Symmetric memory CPU and other

PyTorch does not call malloc or cudaMalloc directly for tensor memory. Each StorageImpl holds a pointer to a c10::Allocator. The allocator returns a DataPtr. The DataPtr holds the address, a context pointer, a deleter function, and the device.

When the last reference to the storage goes away, PyTorch calls the deleter. Thus the allocator controls the free path as well as the allocation path. This is how a caching allocator keeps a freed block for the next request.

Interfaces and registry

All allocators implement one of four interfaces. The first three come from the same base class. The symmetric memory interface is separate because it must also exchange handles between ranks.

How the registry selects an allocator

SetAllocator(type, alloc, priority) writes to a fixed table. The table has one slot for each DeviceType. A call with a lower priority than the current entry has no effect.

REGISTER_ALLOCATOR calls SetAllocator during static initialization. REGISTER_HOST_ALLOCATOR does the same for the host table. The CUDA caching allocator writes its slot when CUDA initializes. On ROCm, it also writes the slot that HIP code reads as CUDA.

To replace the CPU allocator at run time, call c10::SetCPUAllocator(alloc, priority). To replace the CUDA allocator, use torch.cuda.memory.change_current_allocator() before the first CUDA allocation.

Inside the CUDA caching allocator

The default CUDA backend is NativeCachingAllocator. It holds one DeviceCachingAllocator for each GPU. Each device allocator has a recursive mutex, two default block pools, and a map of private pools.

Figure 2 shows one call to malloc. The blue path is the hook that custom MemPools use. Custom MemPools gives the details of that hook. Blocks and segments shows how one layer fills the pools.

Sizes and segments

  • The allocator rounds each request up to a multiple of 512 bytes. With roundup_power2_divisions, it rounds large requests to fractions of a power of two.
  • Requests up to 1 MB use the small pool. The small pool gets 2 MB segments from the driver.
  • Requests from 1 MB to 10 MB get a 20 MB segment by default. Use large_segment_size_mb to change this size.
  • Requests above 10 MB get a segment rounded up to 2 MB.
  • The allocator does not split a cached block larger than max_split_size_mb.

Steps when the cache has no block

  1. Run the registered free-memory callbacks, then search the cache again.
  2. Get a new segment through alloc_block().
  3. Borrow a free block from pools that have use_on_oom=True.
  4. Release cached segments that have no live blocks, then try step 2 again.
  5. Release all cached segments, then try step 2 again. This step does not run during graph capture.
  6. Raise torch.OutOfMemoryError.

Streams and the free path

Each block records the stream that allocated it. get_free_block() returns only blocks from the same stream. When you call tensor.record_stream(s), the allocator records an event on s at free time. The block goes back to its pool only after that event completes.

A freed block goes back to the pool that owns it. A block from a private pool stays in that pool. The allocator joins a freed block with free neighbors in the same segment.

Expandable segments

With expandable_segments:True, the allocator reserves one large virtual address range for each stream. It maps physical pages into the range as the range grows. This decreases fragmentation between segments. Processes cannot share these tensors through CUDA IPC.

Blocks and segments

A segment is one range of device memory. The allocator gets each segment from the driver with one cudaMalloc call. A block is a part of a segment. Each tensor uses one block.

There is no segment object in the code. Each Block has a prev pointer and a next pointer to its neighbors in the same segment, in address order. The first block of a segment has prev = null. To find all of a segment, the allocator follows these pointers.

Reserved memory is the total size of all segments. Allocated memory is the total size of the blocks that tensors use. The difference is cached memory that the next request can use without a driver call.

Rules for a new block

  • Best fit. The allocator takes the smallest free block in the pool that is large enough and was used on the same stream. It does not take the first block by address.
  • No split. If the rest is too small to split, the tensor gets all of the block. The block keeps its full size, and requested_size records the real request.
  • Merge. When a block is freed, the allocator joins it with a free block before it and a free block after it in the same segment.
  • Release. empty_cache() calls cudaFree only for a segment that is one free block. A segment with one live block stays reserved.

      What the walk-through shows

      • Tensors of 10 MiB or more get a segment of their own with no spare space (steps 1 and 7).
      • Small tensors share a 2 MiB segment (steps 2 and 8).
      • Mid-size tensors share a 20 MiB segment. One segment holds the input, the output, the output gradient, and the cuBLAS workspace (steps 3 to 6).
      • The workspace stays allocated in the middle of segment S3. After step 11, S3 has 11.875 MiB free, but in two parts of 6 MiB and 5.875 MiB. A request for 8 MiB cannot use either part and needs a new segment. This is fragmentation.
      • For the same reason, empty_cache() releases nothing at step 12.
      • At step 13, best fit puts the new input in the 5.875 MiB part, not in the 6 MiB part at the lower address.
      Note

      In the next backward pass, weight.grad already exists. The new 32 MiB result of the matrix multiply is then a temporary that AccumulateGrad adds in place and frees. No free block is large enough for it, so the allocator makes another 32 MiB segment. Call optimizer.zero_grad() (which sets gradients to None by default) before backward. The new gradient can then use the block of the old gradient.

      Caution

      The page computes these states from the allocator rules for an Ampere or Ada GPU. On Hopper and Blackwell, the default workspace is 32 MiB, so it gets a segment of its own. Some kernels also make short temporary allocations that this replay does not show. The CUDA context and the cuBLAS handle use memory outside the allocator, so nvidia-smi shows more than the reserved value.

      Custom MemPools

      A MemPool is a private part of the CUDA caching allocator. It has its own small and large block pools. It can also have its own allocator for new segments. Blocks in a MemPool never mix with blocks in the default pools.

      CUDA graph pools use the same mechanism. A torch.cuda.MemPool object and a CUDA graph pool are both a PrivatePool inside the device allocator.

      Parts of a pool

      PartWhereWhat it does
      MempoolId_tMemPool.cppA pair of integers. A pool that you make gets {0, uid}. A pool that a CUDA graph makes gets {uuid, 0}. The value {0, 0} means "no pool".
      PrivatePoolCUDACachingAllocator.cppHolds large_blocks, small_blocks, an optional allocator_, use_count, and a count of live segments.
      graph_poolsdevice allocatorMap from MempoolId_t to PrivatePool. The name is from CUDA graphs. User pools are in the same map.

      no_split_poolsdevice allocatorPools whose blocks the allocator never splits.

      Rules and limits

      Caution

      Routing from use_mem_pool applies to one thread only. The autograd engine runs backward on other threads. Thus gradients that backward allocates do not go into the pool.

      Caution

      With backend:cudaMallocAsync, a MemPool only counts its users. It does not route allocations. PyTorch shows a warning one time.

      Caution

      A custom allocator that calls Python must not run allocator work on many threads at the same time. The native allocator can hold its mutex while it waits for the GIL. Another thread that holds the GIL and waits for the mutex causes a deadlock.

      Note

      The allocator calls the custom free function after it releases its own lock. It keeps the pending frees in a queue until then. This prevents a lock-order deadlock with the callback's own locks.

      Note

      A pool with a custom allocator does not use expandable segments, even when expandable_segments:True is set. You cannot restore an expandable segment into such a pool.

      Note

      With no_split=True, each allocation uses all of the block that it gets. The symmetric memory pool uses this so that no two tensors share one signal pad.

      Note

      use_on_oom=True lends only free blocks that are already in the pool. The fallback does not call the pool's allocator for a new segment.

      Note

      A MemPool belongs to the device that is current when you make it. Use pool.snapshot() to see only the segments of that pool.

def alloc_fn(size, device, stream):
    err, ptr = rt.cudaMalloc(size)

    return int(ptr) if ok else None

    rt.cudaFree(ptr)

      Pinned host memory

      tensor.pin_memory() and pin_memory=True get page-locked host memory. PyTorch finds the host allocator through at::getHostAllocator(device_type). CUDA, XPU, and PrivateUse1 backends use one shared template, CachingHostAllocatorImpl. MPS has its own MPSPinnedAllocator.

      cudaHostRegister pins pages of a normal malloc block. Registration of large blocks is slow. Set pinned_num_register_threads to register the pages on many threads. Use torch.cuda.host_memory_stats() to see the counters of this cache.

      Distributed and symmetric memory

      Symmetric memory gives each rank a buffer of the same size at a known address. Kernels can then read and write peer buffers directly. Each backend uses a SymmetricMemoryAllocator. Use symm_mem.set_backend() to select "CUDA", "NVSHMEM", or "NCCL".

      Both distributed paths connect to the caching allocator through a MemPool. Figure 5 shows the two paths.

      Symmetric memory pool
      import torch.distributed as dist
import torch.distributed._symmetric_memory as symm_mem

symm_mem.set_backend("NCCL")   # or "CUDA", "NVSHMEM"
pool = symm_mem.get_mem_pool("cuda:0")
with torch.cuda.use_mem_pool(pool):
    t = torch.empty(1 << 20, device="cuda:0")

# All ranks must allocate in the same order.
symm_mem.rendezvous(t, dist.group.WORLD.group_name)
      NCCL buffer registration
      pg = dist.group.WORLD
backend = pg._get_backend(torch.device("cuda"))

pool = torch.cuda.MemPool(backend.mem_allocator)
with torch.cuda.use_mem_pool(pool):
    buf = torch.empty(1 << 26, device="cuda")

backend.register_mem_pool(pool)   # symm=True for windows
dist.all_reduce(buf)
backend.deregister_mem_pool(pool)
      Note

      The symmetric pool sets use_on_oom=False. If the pool lent blocks to normal allocations, ranks could get different allocation states. It sets no_split=True because each segment has one signal pad.

      Caution

      Make the NCCL communicator before you call register_mem_pool(). Pass device_id to init_process_group for eager initialization.

      Note

      TORCH_NCCL_USE_TENSOR_REGISTER_ALLOCATOR_HOOK=1 registers every segment of the caching allocator with NCCL, not only the segments of one pool. It is not compatible with expandable segments. PyTorch disables it when expandable segments are on.
