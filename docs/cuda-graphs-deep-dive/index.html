CUDA Graphs Deep Dive

This document tells how CUDA graphs work at the runtime level, without a framework. It covers the graph object model, stream capture rules, update, conditional nodes, memory nodes, and device launch. It ends with failures that engineers report in public, and the tools to find them.

Primary source: CUDA Programming Guide v13.5, §4.2 Style: ASD-STE100 (Simplified Technical English) Companion: PyTorch CUDA Graphs

01 · Overview

Why graphs

A stream launch has a cost for each kernel. The host driver prepares each launch, and the GPU has a gap between kernels. For short kernels, this cost can be a large part of the total time.

A graph is a set of operations with dependencies. You define the graph one time. CUDA validates it and prepares it one time, at instantiation. Then one call launches all of the work. CUDA also sees the full workflow, so it can apply optimizations that piecewise stream submission does not permit.

Launch cost model

NVIDIA measured repeat-launch CPU cost on Ampere (RTX 3060) for straight-line graphs. A straight-line graph is a chain of kernel nodes. Use the calculator to compare your stream cost with the measured graph cost.

02 · Objects

Object model: template and executable

Graph work has three stages: definition, instantiation, and execution. Each stage has its own object.

RuleConsequence
cudaGraph_t objects are not thread-safe.Do not let two threads access one template at the same time.
Only one instance of a cudaGraphExec_t runs at a time.Two launches of one exec into two streams run one after the other. Clone and instantiate again to get parallel runs.
The launch stream gives order only.The stream does not limit the parallelism inside the graph. It does not control where nodes run.
Updates take effect at the next launch.A launch that is running is not affected. You can queue update, launch, update, launch on one stream.

cudaGraphAddNode() is the polymorphic API for all node types. The .type field selects the type. The per-type APIs, for example cudaGraphAddKernelNode(), will be deprecated.

Explicit constructionC++
cudaGraphNodeParams p = {};                 // reserved fields must be zero
p.type                = cudaGraphNodeTypeKernel;
p.kernel.func         = (void*)reduce;
p.kernel.gridDim      = dim3(blocks);
p.kernel.blockDim     = dim3(256);
p.kernel.kernelParams = args;               // copied now, not at launch
cudaGraphAddNode(&k, graph, deps, /*edgeData=*/NULL, nDeps, &p);
p = {};                                     // zero again before the next node

Edge data

Since CUDA 12.3, an edge can carry data: an outgoing port, an incoming port, and a type. Zero data is a full dependency with memory synchronization. The only non-default type is cudaGraphDependencyTypeProgrammatic. It gives Programmatic Dependent Launch (PDL) between two kernel nodes.

ProgrammaticEvent, triggerAtBlockStart = 0type Programmatic, from port …PortProgrammatic
ProgrammaticEvent, triggerAtBlockStart = 1type Programmatic, from port …PortLaunchCompletion
Note
If you query edges and pass no edge-data array, the call fails with cudaErrorLossyQuery when it would discard non-zero edge data. Old code that ignores edge data can fail on graphs that use PDL.
04 · Creation

Stream capture

cudaStreamBeginCapture() puts a stream in capture mode. Work sent to the stream does not run. CUDA adds it to an internal capture graph. cudaStreamEndCapture() returns the graph and ends capture mode.

  • You can capture any stream except cudaStreamLegacy (the NULL stream). cudaStreamPerThread is permitted.
  • End the capture on the stream that started it: the origin stream.
  • If the mode is not Relaxed, call Begin and End from the same thread. Otherwise End returns cudaErrorStreamCaptureWrongThread (908).
  • cudaStreamBeginCaptureToGraph() captures into a graph that you supply, for example the body of a conditional node.

Fork and join with events

A captured event is a set of nodes, not a point in time. If another stream waits on a captured event, that stream also enters capture mode. Both streams then add nodes to the same capture graph.

Capture introspection

cudaStreamGetCaptureInfo() returns the status, a capture ID that is unique in the process, the capture graph, and the dependency set for the next node. Use it to get the handles of the last captured nodes. cudaStreamUpdateCaptureDependencies() adds to (default) or replaces that set. Data other than the status is valid only if the call succeeds and the status is Active.

Caution
When a stream leaves capture mode, the next non-captured item in the stream still depends on the last non-captured item before capture. Capture cuts the dependency only for the items in the capture.
05 · Threads

Capture modes

Some APIs are potentially unsafe during capture. cudaMalloc is the example in the reference. It can make an implicit synchronization, and capture does not record it. The capture mode controls which threads can call these APIs.

Two modes apply. The capture's mode is the argument to cudaStreamBeginCapture. The thread's interaction mode is a per-thread value. It is Global by default. cudaThreadExchangeStreamCaptureMode changes it.

Thread's modeThis thread cannot call unsafe APIs if…
Global (default)this thread has a capture that did not start as Relaxed, or any other thread has a capture that started as Global.
ThreadLocalthis thread has a capture that did not start as Relaxed. Captures in other threads are ignored.
Relaxednever. But calls that necessarily conflict with capture still fail, for example cudaEventQuery on an event last recorded in a capture.

Simulator

Thread A captures. Thread B does not. Select the modes and an API call. The result applies the rules from the Runtime API reference.

Library pattern: allow one unsafe call during captureC++
cudaStreamCaptureMode m = cudaStreamCaptureModeRelaxed;

cudaMalloc(&p, bytes);                       // runs now, at capture time; NOT a graph node

Caution
Relaxed mode permits the call, but the call is not recorded. A cudaMalloc runs one time, at capture. Replay uses the same address. If the memory must be new at each launch, use cudaMallocAsync in the capture. That makes a memory node.
06 · Errors

Prohibited operations and invalidation

Captured work is not scheduled. Thus you cannot synchronize or query a capturing stream or a captured event. You also cannot synchronize a broader handle, for example the device or the context, while any of its streams captures.

If you try an invalid operation, CUDA invalidates the capture graph. Every later use of the capturing streams or captured events returns an error. cudaStreamEndCapture() then removes the streams from capture mode, returns an error, and returns a NULL graph.

CodeNameTypical trigger
900cudaErrorStreamCaptureUnsupportedSync, query, or unsafe call (cudaMalloc, pinned alloc) during capture. Unsupported API, for example cudaStreamAttachMemAsync.
901cudaErrorStreamCaptureInvalidatedAny call after an earlier error in the same capture.
902cudaErrorStreamCaptureMergeA stream in capture A waits on an event from capture B.
903cudaErrorStreamCaptureUnmatchedEndCapture on a stream that did not begin the capture.
904cudaErrorStreamCaptureUnjoinedA forked stream did not join back to the origin stream.
905cudaErrorStreamCaptureIsolationCaptured work waits on non-captured work, for example an event recorded before capture, without cudaEventWaitExternal.
906cudaErrorStreamCaptureImplicitUse of the legacy stream while a blocking stream captures. Synchronous APIs such as cudaMemcpy use the legacy stream.
907cudaErrorCapturedEventQuery or sync on an event last recorded in a capture.
908cudaErrorStreamCaptureWrongThreadNon-Relaxed capture ended from a different thread.
Rule
CUDA prefers to return an error than to ignore a dependency between captured and non-captured work. The one exception is the mode change itself. Begin and End cut the dependency between items before and after the change.
07 · Execution

Instantiate, upload, launch

Full cycleC++
cudaStreamBeginCapture(s, cudaStreamCaptureModeGlobal);
step(s);                                        // kernels, copies, library calls
cudaStreamEndCapture(s, &graph);                // check the return code and graph != NULL

cudaGraphInstantiateParams ip = {};
ip.flags        = cudaGraphInstantiateFlagUpload;
ip.uploadStream = s;                            // upload now, into the launch stream
cudaGraphInstantiateWithParams(&exec, graph, &ip);
if (ip.result_out != cudaGraphInstantiateSuccess) { /* ip.errNode_out names the node */ }

for (;;) cudaGraphLaunch(exec, s);              // same stream each time
Instantiate flagEffectConstraint
AutoFreeOnLaunchBefore a relaunch, frees allocations from the previous launch that are still live.Not with DeviceLaunch. Does not change destroy: you must still free live allocations.
UploadUploads the graph into uploadStream after instantiation.WithParams only. Not returned by cudaGraphExecGetFlags.
DeviceLaunchThe exec can launch from host and device.Unified addressing required. Single device. See 11.
UseNodePriorityKernel nodes use their own priority attribute, not the priority of the launch stream.Capture copies the stream priority into each kernel node. Without the flag, CUDA ignores it.
  • If a graph has memory nodes or device-updatable kernel nodes, only one exec of it can exist at a time.
  • If a launch finds live allocations from the previous launch and the exec has no AutoFreeOnLaunch, the launch fails with cudaErrorInvalidValue.
  • The first launch uploads work descriptors to the GPU, at O(n) CPU cost. cudaGraphUpload moves that cost out of the critical path. Uploads of one exec are serialized.
  • Upload into one stream and launch into another acts like a stream change. CUDA can then remap memory.
08 · Update

Updating an instantiated graph

Capture records every launch configuration and argument by value. If a value changes, the exec is stale. Re-instantiation is expensive. An update changes parameters in place, if the topology stays the same.

MethodAPIUse when
Whole graphcudaGraphExecUpdate(exec, newGraph, &info)Many nodes change, or a library made the graph and you do not have the node handles.
Individual nodecudaGraphExecKernelNodeSetParams, …MemcpyNodeSetParams, …MemsetNodeSetParams, …HostNodeSetParams, …ChildGraphNodeSetParams, …EventRecord/WaitNodeSetEvent, …ExternalSemaphores…Few nodes change and you have their handles. No topology compare, so it is faster.
Enable / disablecudaGraphNodeSetEnabledKernel, memset, and memcpy nodes. A disabled node acts as an empty node. Its parameters stay.
Device-sidecudaGraphKernelNodeUpdatesApply, …SetParam, …SetGridDim, …SetEnabledA kernel in the graph changes a device-updatable node on the same device. The next host upload or launch overwrites these changes.

Update checker

Select what changed. The result tells which path works.

Whole graph update: node pairing

cudaGraphExecUpdate pairs nodes of the old and new graph by the order of API calls. To get a deterministic pairing, obey these rules:

  1. For each capturing stream, make the API calls in the same order. This includes event waits and other calls that make no node.
  2. For each node, make the calls that change its incoming edges in the same order. Keep the same order inside dependency arrays.
  3. Make the calls that create or affect sink nodes in the same order: node adds that make a sink, edge removals that make a sink, cudaStreamUpdateCaptureDependencies that removes a sink, and cudaStreamEndCapture.
Caution
If threads issue captured work in a different order on each iteration, the update fails with TopologyChanged, even if the final graph looks the same. On failure, destroy the exec and instantiate again.

Pattern: capture plus one explicit node

NVIDIA shows a combined method for a kernel whose arguments change on each launch. Capture the static kernels. Add the dynamic kernel explicitly, inside the capture, and keep its handle.

Insert an explicit node into a live captureC++
cudaStreamCaptureStatus st; cudaGraph_t g; const cudaGraphNode_t* deps; size_t n;
cudaStreamGetCaptureInfo(s, &st, NULL, &g, &deps, NULL, &n);
cudaGraphAddNode(&dyn, g, deps, NULL, n, &kernelParams);   // keep 'dyn'
cudaStreamUpdateCaptureDependencies(s, &dyn, NULL, 1,
                                    cudaStreamSetCaptureDependencies);
// ... continue capture, end, instantiate. Before each launch:
cudaGraphExecKernelNodeSetParams(exec, dyn, &newParams);
Method (A100, launch-bound workload)TimeSpeedup
No graph706 ms1.00×
Capture again + cudaGraphExecUpdate each time580 ms1.22×
Capture once + explicit node + SetParams433 ms1.63×
Note
The third option is indirection. The kernel reads its changing value from device memory, and you write that memory before the launch. Then no update is necessary. llama.cpp PR #9017 used this method for its KV-cache copy kernels and measured about 1–2% gain.
09 · Control flow

Conditional nodes

A conditional node runs a body graph based on a value on the device. The CPU does not take part. The value is in a cudaGraphConditionalHandle. A kernel sets it with cudaGraphSetConditional().

Handle rules

  • Create the handle before the node. One handle belongs to one conditional node. You cannot destroy a handle.
  • With cudaGraphCondAssignDefault, CUDA sets the default value at the start of each launch. Without it, the value is undefined at each launch. Do not expect it to persist between launches.
  • Whole graph update also updates the handle default and flags. Create and assign handles in the same order in both graphs.

Body graph requirements

  • All nodes on one device.
  • Only kernel, empty, memcpy, memset, child graph, and conditional nodes. No host, event, or memory nodes.
  • No CUDA Dynamic Parallelism. No device graph launch from body kernels.
  • Cooperative launches are permitted if MPS is not in use (v13.5 guide). Older NVIDIA blog text says cooperative launches are not supported. Check your version.
  • Memcpy and memset only on device memory or pinned device-mapped host memory. No CUDA arrays. The device that holds the graph does the copy.
10 · Memory

Graph memory nodes

A graph can own allocations. Capture of cudaMallocAsync and cudaFreeAsync makes alloc and free nodes. The lifetime rules are GPU ordered: the lifetime starts when GPU execution reaches the alloc node. It ends at the free node, at a cudaFreeAsync in stream order, or at once with cudaFree.

Restrictions on graphs with memory nodes

  • You cannot delete nodes or edges. You cannot clone the graph.
  • Only one exec of the graph can exist at a time.
  • You can use the graph as a child only if you move ownership to the parent (CUDA 12.9). A moved child cannot be instantiated, destroyed, or updated alone.
  • You can free an allocation in the owning graph or in another graph, but not in both.
  • Graph destruction does not free live allocations. Free them in another graph, or with cudaFreeAsync or cudaFree.
  • Peer access for captured allocations is the pool's peer access at capture time. Later changes to the pool do not change the graph.

Footprint

The graph memory pool is separate from the stream-ordered allocator pools. cudaMemPoolTrimTo does not trim it. After you destroy graphs, CUDA keeps the physical memory. cudaDeviceGraphMemTrim releases memory that no unfreed allocation and no scheduled graph uses.

Attribute (cudaDeviceGetGraphMemAttribute)Value
cudaGraphMemAttrReservedMemCurrentPhysical memory that the driver reserves for graph allocations in this process.
cudaGraphMemAttrUsedMemCurrentPhysical memory that at least one graph maps now.
11 · Device

Device graph launch

A kernel can launch a graph with cudaGraphLaunch, with the same signature as on the host. The graph must be instantiated with cudaGraphInstantiateFlagDeviceLaunch and uploaded before the first device launch. A host launch also uploads it. A device launch must come from a kernel that is in another graph.

Named stream (device only)Mode
cudaStreamGraphFireAndForgetStarts at once, as a child of the launching graph's environment.
cudaStreamGraphTailLaunchStarts when the launching environment is complete. Tail launches run one at a time, in queue order.
cudaStreamGraphFireAndForgetAsSiblingStarts at once, as a child of the parent environment.
  • Device graphs: one device; only kernel, memcpy, memset, and child graph nodes; no CUDA Dynamic Parallelism.
  • A second device launch of a graph that is still running returns cudaErrorInvalidValue. Host and device launch at the same time is undefined behavior.
  • Device launch is per thread. Select one thread to launch.
  • After a host update, upload the exec again. A device launch during an update is undefined behavior.
12 · Lifetime

CUDA user objects

A graph can use a resource after the code that captured it returns. A user object attaches a destructor to a reference count, like shared_ptr. Graphs can own references.

Give the only reference to the graphC++
cudaUserObject_t obj;
cudaUserObjectCreate(&obj, res, destroyRes, 1, cudaUserObjectNoDestructorSync);
cudaGraphRetainUserObject(graph, obj, 1, cudaGraphUserObjectMove);
// clone: copies references. instantiate: exec retains a copy.
// exec destroyed while running: CUDA keeps references until work completes.
  • References in a child graph belong to the child, not the parent.
  • The destructor must not call CUDA APIs. It runs on a CUDA internal thread, like a host function.
  • No API waits for a destructor. Signal your own sync object from the destructor if you need to wait.

Procedure: isolate a capture failure

  1. Run the same code without capture. Make sure that it gives correct results.
  2. Run it one time more without capture. This loads modules and initializes libraries.
  3. Check the return code of each call in the capture region. Record the first error that is not 901.
  4. If the error is 900, find a sync, query, or allocation. Look in other threads too.
  5. If the error is 904 or 905, draw the event edges. Make sure that each side stream forks from and joins to the origin stream.
  6. If the capture fails only with other threads active, capture again in ThreadLocal mode.
  7. After EndCapture, dump the graph with cudaGraphDebugDotPrint. Make sure that the node count is correct.
